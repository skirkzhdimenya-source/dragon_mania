# DragonML: разблокировка обмена для Zilarranjo (UID 1370)

Дата расследования: 2026-10-23/24  
Среда: BlueStacks Air на macOS, Android 13, Frida 17.24.3  
Модуль: `libDML.so`  
Цель: выяснить, почему карточка Zilarranjo показывает `BUY GENERATOR`, хотя соседние карточки показывают `EXCHANGE PARTS`, и проверить, можно ли провести именно обмен.

> **Итог:** узкий runtime-хук в `libDML.so+0x1987670`, срабатывающий только для UID 1370 при исходном байте регистра `x9 == 1`, заменяет значение `x9` на 0. После этого карточка проходит по обычной ветке выбора оформления, показывает `EXCHANGE PARTS`, а пользователь вручную нажал эту кнопку и получил один puzzle piece. Это подтверждает успешность хотя бы одного обмена в проверенной сборке. Патч действует только пока Frida подключена и не изменяет APK или постоянные игровые данные.

## 1. Сравнили трёх драконов в конфиге

В `dragon_types.json` сравнили UID 1368, 1369 и 1370:

| UID | Dragon ID | Элементы |
|---:|---|---|
| 1368 | `D_ANCIENT_VOID_WATER_UPD84` | Ancient / Void / Water |
| 1369 | `D_ANCIENT_VOID_FIRE_UPD84` | Ancient / Void / Fire |
| 1370 | `D_ANCIENT_METAL_WIND_UPD84` | Ancient / Metal / Wind |

У всех троих в выгрузке одинаковы ключевые значения: `NEW_RARITY = SUPREME`, `RARITY = ANCIENT`, DLC `game_dlc_upd84`, `PARTS_REQUIRED = 500`, `AVAILABLE_FOR_ORB = no`. Эти записи сами по себе не объясняют, почему у одной карточки другой текст кнопки. Поэтому дальше исследовали runtime-модель карточки.

## 2. Нашли модель карточки и флаг оформления кнопки

Getter `VM_ShopDragonCard` был найден по адресу `libDML.so + 0x20215AC`. В наблюдаемой модели:

- `model + 0x108` содержит UID дракона;
- `model + 0xC8` указывает на bindable-строку имени;
- `model + 0xE0` указывает на объект bindable boolean для `useExchangeButtonDesign`; значение boolean в прочитанном объекте находилось по `+0x50`.

Снятые значения:

| UID | Имя | `useExchangeButtonDesign` |
|---:|---|---|
| 1370 | ZILARRANJO | `false` |
| 1368 | PROTOS ONDA | `true` |
| 1369 | PROTOS VATRA | `true` |

У вложенных объектов кнопки в памяти также читались строки `btnAction62`, `btnAction64`, `btnAction66` для UID 1370, 1368 и 1369 соответственно. Само по себе это наблюдение не доказывает, какое именно действие выполняет каждый идентификатор; оно было сохранено как вспомогательная зацепка.

## 3. Проверили значения перед выбором оформления

Трассировка участка, начинающегося около `libDML.so + 0x19873FC`, показала для всех трёх карточек:

- `field + 0x38 = 500`;
- `currentValue = 0`;
- `computedFlag = 0`.

То есть обычное вычисленное значение и порог фрагментов у этих трёх карточек совпадали.

Затем сравнили ветвление функции. В трассировке точка `libDML.so + 0x1987670` показывала:

- **UID 1370:** байт в `x9` равен 1; выполнение уходит в отдельную ветку и не достигает обычного назначения решения;
- **UID 1368 и 1369:** байт в `x9` равен 0; функция достигает обычной ветки `PASS` и `DECISION`, которая выставляет оформление обмена.

Поэтому наиболее точное описание причины: в исследованной сборке у Zilarranjo другой runtime-путь на контрольной точке `+0x1987670`. Семантическое название исходного признака, кодируемого этим байтом, отдельно не установлено.

## 4. Сделали контролируемую проверку гипотезы

В тестовом диагностическом хукe регистр `x9` менялся только при одновременном выполнении условий:

1. выполнение дошло до `libDML.so + 0x1987670`;
2. объект, указанный в `x21`, имеет UID 1370;
3. младший байт `x9` равен 1.

В этом случае выполнялось `this.context.x9 = ptr('0x0')`. Записи в сам объект карточки или в конфигурационный файл не было.

Лог теста:

```text
[SHOPFORCE][GATE] uid=1370 originalFlag=1 -> w9=0
[SHOPFORCE][DECISION] reached normal decision branch computedFlag=0
```

Пользователь подтвердил, что после этого карточка Zilarranjo стала показывать `EXCHANGE PARTS`, как и две соседние карточки.

## 5. Проверили не только надпись

После изменения оформления пользователь вручную нажал `EXCHANGE PARTS` и сообщил, что получил один puzzle piece. Это важно: проверка подтвердила хотя бы один успешный обмен, а не только смену текста на карточке. Повторяемость и поведение на других событиях/версиях игры этим единичным тестом не проверены.

## 6. Рабочий скрипт

Сохранить как:

`$HOME/Downloads/frida-dml/enable_zilarranjo_exchange.js`

```javascript
'use strict';

const mod = Process.findModuleByName('libDML.so');
if (mod === null) throw new Error('libDML.so not found');

let logged = false;

Interceptor.attach(mod.base.add(0x1987670), {
    onEnter: function () {
        try {
            const row = this.context.x21;
            if (row.isNull() || row.readS32() !== 1370) return;
            if ((this.context.x9.toInt32() & 0xff) !== 1) return;

            this.context.x9 = ptr('0x0');

            if (!logged) {
                console.log('[ZILARRANJO] EXCHANGE PARTS enabled');
                logged = true;
            }
        } catch (_) {}
    }
});

console.log('[ZILARRANJO] READY');
```

Запуск из терминала macOS:

```bash
source "$HOME/.venvs/frida/bin/activate"
adb connect 127.0.0.1:5555
adb -s 127.0.0.1:5555 forward tcp:27042 tcp:27042
frida -H 127.0.0.1:27042 -n DragonML -l "$HOME/Downloads/frida-dml/enable_zilarranjo_exchange.js" 2>&1 | tee "$HOME/Downloads/frida-dml/enable_zilarranjo_exchange.log"
```

Дождаться `[ZILARRANJO] READY`, открыть экран магазина драконов и самостоятельно нажать `EXCHANGE PARTS`. Скрипт не выполняет нажатие автоматически. После полного перезапуска процесса игры нужно снова подключить Frida и запустить скрипт. Остановка сессии Frida прекращает действие runtime-хука.

## 7. Что не сработало и чего избегать

Ранее пробовали глобально перехватывать часто вызываемые функции сравнения строк/памяти — `strcmp`, `strncmp`, `strstr`, `memcmp`. Такой перехват вызвал сильное торможение/зависание игры из-за огромного числа срабатываний. Его не следует запускать повторно для этой задачи: причина кнопки уже локализована узким перехватом.

Не считать доказанными следующие вещи:

- точный смысл байта, который проверяется в `x9`;
- точное назначение `btnAction62` без отдельного анализа диспетчеризации;
- работоспособность смещений после обновления игры или изменения сборки.

Смещения здесь относительные, от базы загруженного `libDML.so`; базовый адрес модуля меняется между запусками. Скрипт предназначен для проверенной сборки и использует ARM64-регистры наблюдавшегося процесса. Если игра обновится или скрипт перестанет менять кнопку, не следует вслепую применять старые смещения: сначала нужно заново проверить функцию и ветвление.
